# crewAI GaussDB 适配 — 测试指南

> 五层测试金字塔：L1 连通 → L2 SQL 契约 → L3 持久化 → L4 向量 → L5 Ollama 端到端。
> 执行入口：`uv run python delivery/tests/run_all.py [--with-ollama]`（退出码 0=全过，1=有失败）。

## 0. 测试前置

1. `.env`（或进程环境）填好 `GAUSSDB_*` 连接变量（模板 `.env.gaussdb.example`）
2. 在 crewAI uv workspace 根目录执行（L3/L4 需要 `crewai[gaussdb]` 环境）
3. **串行执行**：集成测试对共享库做 DDL，xdist 并行会竞态——统一 `-n 0`（run_all 已内置）
4. L5 需要 Ollama 服务 + `bge-m3` embedding 模型（可选 `qwen3:4b` LLM）

## 1. 分层说明

### L1 — t1_connectivity.py（连通性，纯 psycopg2）

验证：版本 ≥507、兼容模式为 Oracle 兼容（A/ORA）、`enable_vectordb` 状态、拓扑（pgxc_node：集中式空表/分布式 >0）、建表权限。
预期：全部 PASS；`enable_vectordb=off` 时提示向量功能需开启（不阻塞 L1）。

### L2 — t2_sql_smoke.py（SQL 方言契约，纯 psycopg2）

验证 O 模式关键方言（每条一条断言，测试表用后即删）：
- MERGE INTO 单行/批量（jsonb 载荷）可用；`ON CONFLICT` 确认不可用（预期报错）
- SEQUENCE + DEFAULT nextval；INSERT RETURNING
- JSONB `->>` 过滤；floatvector cast 与 `<+>` 检索；科学计数法字面量往返
预期：全部 PASS。任何 FAIL 说明目标实例方言与适配基线不符（参考注意事项 §2）。

### L3 — t3_persistence.py（持久化端到端，依赖 crewai[gaussdb]）

验证三个关系存储点 + 接线（真实 GaussDB，测试表用后清理）：
- Flow：GaussDBFlowPersistence save/load（最新覆盖）/ pending_feedback MERGE 覆盖 + clear
- Kickoff：add（MERGE 覆盖）/ update（rowcount 告警路径）/ load 列序 / delete_all
- Checkpoint：GaussDBProvider checkpoint/from_checkpoint/prune（seq 保序）/ async
- 接线：`CREWAI_STORAGE_BACKEND=gaussdb` 下工厂/handler/detect_provider 三路切换
预期：全部 PASS。

### L4 — t4_vector.py（向量端到端，依赖 crewai[gaussdb]）

验证两条向量链路（真实 GaussDB，假确定性向量）：
- Memory：8 维全方法 roundtrip（save/search/score/update/delete/count/scopes/categories/reset）+ 维度不匹配异常 + **1536 维 DiskANN+PQ 端到端**（pg_indexes 断言 gsdiskann + pq_nseg=96）
- Knowledge：add（doc_id 幂等覆盖）/ search（score 公式 + metadata_filter 参数化）/ 1536 维 DiskANN 端到端 / delete_collection
- 分布式实例上 >1024 维建表被拒（门禁拒绝语义；集中式上 skip）
预期：全部 PASS（1 个 skip 为正常——分布式门禁测试仅在分布式实例运行）。

### L5 — t5_e2e_ollama.py（全流程端到端，真实 Ollama 模型，可选）

三层真实模型验证（非 mock）：
1. Knowledge 语义检索：Ollama bge-m3 embedding → Knowledge → GaussDB → 语义查询命中
2. Memory remember/recall：qwen3 LLM 提取（EncodingFlow）→ bge-m3 → GaussDB → 召回
3. Crew 全流程：Crew(llm=qwen3, knowledge_sources, memory=True) → kickoff 从知识库正确回答
预期：PASS。详见 t5 脚本内注释。

## 3. 与仓库测试套件的关系

`delivery/tests/` 是**独立交付验证脚本**（不依赖 pytest、自包含凭据读取）；仓库内的 pytest 套件（`lib/crewai/tests/**`，`GAUSSDB_TEST=1` 门控 + `-n 0`）是开发回归用，两者共用同一批被测代码。

**既有失败基线说明**（跑仓库全量 pytest 时会看到，与本适配无关）：
- `lib/cli/tests` 约 70 failed/13 errors：pytest-recording `--block-network` 拦 Windows asyncio socketpair（既有）
- `lib/crewai/tests/test_checkpoint.py` 18 failed：同源既有环境问题
- memory/rag 的零星 failed：docling/qdrant 等可选依赖未安装
适配新增的 ~120 个测试在上述环境全绿。

## 4. 常见失败排查

| 症状 | 原因 | 处理 |
|---|---|---|
| SASL authentication not supported | 实例 sha256 认证，开源 psycopg2 不支持 | 按注意事项 §1 配 md5 |
| dimensions cannot exceed 1024 | 分布式实例 + 高维 embedding | 换 ≤1024 维模型或集中式 |
| vectordb indexes supported only by high-order features | `enable_vectordb=off` | gs_guc 开启 + 重启集群 |
| relation does not exist (测试中) | 上个测试清理后未重建 / 并行执行 | 确认 `-n 0`；单独重跑该层 |
| LockException | 并发进程写同一库且无 REDIS_URL | 单机确认锁文件同 TMPDIR；跨机配 REDIS_URL |
